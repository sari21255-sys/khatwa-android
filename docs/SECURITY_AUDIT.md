# التدقيق الأمني
المراجع: `TECHNICAL_AUDIT_REPORT.md`. الحالة بعد الإصلاح:

| البند | الحالة |
|---|---|
| XSS | مُغلق: `esc()` على كل نص مستخدم (يشمل `'`)، واختبار آلي بحمولات في الاسم والتمرين والوجبة |
| تلوّث النموذج الأولي من استيراد/مزامنة | مُغلق: `cleanData()` + اختبار |
| بيانات مستوردة تالفة | مُغلق: `validState()`؛ لا تغيير عند الرفض |
| فقدان صامت للبيانات عند امتلاء التخزين | مُغلق: تنبيه |
| إخفاء المنشورات/تضخيم الإعجابات من العميل | مُغلق: قيود RLS + اختبار |
| بلاغات الحسابات الوهمية | مخفَّف: تُحتسب بلاغات حسابات عمرها > يوم فقط |
| تكلفة الذكاء الاصطناعي | مخفَّف: حد IP + سقف يومي كلي + حد حجم الصورة |
| CORS | مُغلق: قائمة نطاقات صريحة |
| كلمات المرور في الوسيط | PBKDF2-SHA256 بـ100,000 دورة (الحد الأقصى في Workers) مع ملح لكل مستخدم |
| رمز الوسيط سرّ دائم | قائم: خطر مقبول للحالة الشخصية؛ الحل البنيوي هو الاعتماد على Supabase JWT (مقترح، يحتاج قرارك) |
| حدود KV غير ذرّية | قائم ومُوثّق: السقف الكلي يغطي التكلفة؛ Durable Objects إن ظهر إساءة |
| تأكيد البريد | قرار إعداد في Supabase: يُنصح بتفعيله قبل فتح المجتمع |
| `target=_blank` | كلها `noopener` |
| المفاتيح | لا مفاتيح في الشيفرة؛ `ANTHROPIC_API_KEY` سرّ في Cloudflare، ومفتاح Supabase المستخدم هو anon العام بحسب تصميمه |
